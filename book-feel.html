Chapter Three

Working with Data Types

❦

Every value a program stores has a type — a promise about what the value means and what you are allowed to do with it. Types are the grammar of a language: they decide which sentences are meaningful and which are nonsense, long before the program ever runs.

Before we write a single line, it is worth slowing down here. Almost every confusing bug a beginner meets in their first month traces back to a value being a different type than they assumed. Learn to see types, and a whole class of problems simply stops happening.

3.1 · The four families

Python groups its built-in types into four families you will meet constantly. Numbers count and measure. Text carries meaning for humans. Collections hold many values at once. Booleans answer yes-or-no questions and drive every decision the program makes.

NoteA fifth family, None, represents the deliberate absence of a value. It appears in chapter 5.

Notice that each family answers a different question. Confusing two of them — asking a number to behave like text, or a collection to behave like a single value — is the most common source of errors at this stage.

A type is not a restriction. It is a promise the language makes back to you.

3.2 · Seeing a type directly

Python will always tell you what it thinks a value is, if you ask. The habit of asking — rather than assuming — is worth building now, while the programs are small enough that the answer is never a surprise.

Worked example 3.1

Given x = 7 and y = "7", predict the result of x + y before reading on. If you expected 14, you assumed both were numbers. If you expected "77", you assumed both were text. Python does neither — it refuses, because addition between a number and a string has no agreed meaning.

That refusal is a feature. A language that guessed would silently produce a wrong answer that surfaces three hundred lines later, in a place that has nothing to do with the mistake.
